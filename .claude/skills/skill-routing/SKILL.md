# skill-routing

Встроенный выбор скиллов по описанию срабатывает редко. На прямую просьбу с кодом модель делает работу сама и скилл не вызывает (agent-skills, issue #620). Этот скилл заменяет выбор по описанию явной таблицей событий.

Скилл экспериментальный. Человек проверяет, какие скиллы срабатывают на реальных задачах. Поэтому каждое решение о маршруте пиши вслух, см. «Журнал».

## Как работать

Правила ниже действуют до конца сессии, а не только для текущего сообщения.

1. Перед каждым шагом сверь его с таблицей событий. Шаг — это новое сообщение человека или событие посреди работы: упал тест, появился новый вызов внешнего API, дошло до коммита.
2. Если событие совпало, сначала вызови скилл через инструмент Skill, потом делай работу. Не пересказывай скилл по памяти: его шаги нужно загрузить.
3. Событие совпало, даже если задача кажется простой, код уже вставлен в сообщение или в просьбе нет нужных слов. Пример: «почини определение созвона» — это баг, хотя слов «тест» и «отладка» в просьбе нет.
4. Если совпало несколько событий, вызови скиллы в порядке таблицы: сначала понять задачу, потом спроектировать, потом писать код, потом проверить.
5. Один скилл в одной задаче вызывай один раз. Для новой задачи в той же сессии вызывай снова.
6. Если человек сам запустил slash-команду, она главная. Но события посреди работы все равно проверяй. Пример: `/build` добавляет запрос к внешнему провайдеру, значит, нужен еще `security-and-hardening`.
7. Не вызывай `using-agent-skills`. Этот скилл его заменяет.
8. Стадии issues ведет скилл `using-issues` по корневому `AGENTS.md`. Его правило «не запускай следующий шаг без „да“» остается в силе. Этот скилл подключает скиллы внутри текущего шага, а стадии не перескакивает.

## Журнал

Человек по журналу проверяет маршрутизацию, поэтому пиши его всегда.

- В начале ответа на каждое сообщение человека пиши одну строку:
  - `Маршрут: <скилл> — <событие из таблицы>`, если вызываешь скилл;
  - `Маршрут: без скилла — <почему ни одно событие не подходит>`, если не вызываешь.
- Посреди работы, перед вызовом скилла, пиши такую же строку.
- Если событие подходит, а скилл ты решил не вызывать, напиши это и причину. Такие случаи человеку важнее всего.
- На вопрос «какие скиллы вызваны» перечисли их по порядку с событиями.

## Таблица событий

### Понять задачу

| Событие | Скилл |
|---|---|
| Неясно, кому и зачем это нужно, как поймем, что готово, или чем можно пожертвовать. Просьба вида «сделай X» без деталей | `interview-me` |
| Цель ясна, но решить можно по-разному. Человек просит «подумай», «какие варианты», «проверь идею» | `idea-refine` |
| Перед решением, которое трудно отменить: миграция данных в Firestore, удаление данных пользователя, смена модели или провайдера по умолчанию, формат данных, который уже читают выпущенные клиенты | `doubt-driven-development` |
| Ты собираешься утверждать неочевидное: «это безопасно», «это выдержит нагрузку», «это соответствует спеке» | `doubt-driven-development` |

### Спроектировать

| Событие | Скилл |
|---|---|
| Новая фича, изменение затрагивает несколько модулей, работа дольше одного захода | `spec-driven-development` |
| Есть спека или требования, нужно разбить их на задачи | `planning-and-task-breakdown` |
| Новый IPC-канал между main и renderer в desktop, новый или измененный эндпоинт в `backend/routers/`, изменение моделей pydantic в ответах API, новые поля или индексы Firestore, изменение `contracts/` | `api-and-interface-design` |
| Замена старого кода, API, модели или библиотеки. Удаление поля в Firestore. Удаление кода, на который кто-то еще опирается | `deprecation-and-migration` |
| Нет записанной планки качества или ее хотят поменять: покрытие, лимиты, проверки в хуках. Перед `/build auto` | `constraint-driven-development` |
| Принято архитектурное решение, выбран один подход из нескольких, изменилось поведение приложения для человека | `documentation-and-adrs` |

### Писать код

| Событие | Скилл |
|---|---|
| Изменение затрагивает больше одного файла | `incremental-implementation` |
| Новая логика, изменение поведения, исправление бага, просьба добавить тесты | `test-driven-development` |
| Упал тест, сборка, `typecheck` или `lint`. Ошибка в логах приложения или бэкенда. Приложение ведет себя не так, как ожидали. Раньше работало, а теперь нет. Даже если причина кажется очевидной | `debugging-and-error-recovery` |
| Код пишется по памяти для конкретной библиотеки: Electron, electron-vite, React, Vitest, FastAPI, pydantic, Firestore, httpx, LangChain, Deepgram, OpenRouter, PipeWire. Особенно если API мог поменяться | `source-driven-development` |
| Данные из renderer в main через IPC, токены Firebase и ключи провайдеров, запросы к внешним провайдерам, снимки экрана, звук и расшифровки, персональные данные, разрешенные адреса и CORS, все, что может уйти в контур Omi | `security-and-hardening` |
| Новый внешний вызов, фоновая задача, повторные попытки, очередь, долгое WebSocket-соединение. По логам не удалось понять, что случилось | `observability-and-instrumentation` |
| Замерили медленную работу: долгий запуск, долгий ответ API, рост очереди, большой расход памяти. Блокирующий вызов в async-коде бэкенда. Код работает с большими объемами данных | `performance-optimization` |
| Интерфейс: renderer в `desktop/windows`, страницы `web/app` и `web/admin` | `frontend-ui-engineering` |
| Нужно проверить результат в браузере: консоль, сеть, верстка | `browser-testing-with-devtools` |

### Проверить и выкатить

| Событие | Скилл |
|---|---|
| Код работает и тесты проходят, но его трудно читать. Человек просит «упрости», «отрефактори» | `code-simplification` |
| После фичи или исправления бага. Нужно оценить код другого агента. Человек просит ревью | `code-review-and-quality` |
| Коммит, ветка, worktree, PR, конфликт при мерже, слияние из `upstream/main`, разбор грязного рабочего дерева | `git-workflow-and-versioning` |
| Изменение `lefthook.yml`, скриптов в `package.json`, скриптов проверок в `backend/scripts/`, `deploy/local/docker-compose.yaml`, `.github/workflows/`. Упала проверка в хуке | `ci-cd-and-automation` |
| Перед мержем в main: после него CI собирает desktop и web. Сборка релиза desktop через electron-builder | `shipping-and-launch` |
| Агент путает соглашения проекта, придумывает несуществующие API. Нужно поменять `AGENTS.md` или правила | `context-engineering` |

## Что делать после задачи

Когда задача закончена, допиши в ответ короткий итог для проверки:

- какие скиллы вызваны и на какие события;
- какие события совпали, но скилл не вызван, и почему;
- какую строку таблицы стоит поправить, если она сработала зря или не сработала.
