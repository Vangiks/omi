# using-issues

Скилл ведет issue по стадиям. Сам он код не пишет: он выбирает скилл agent-skills, запускает его, а после шага записывает результат в issue и меняет стадию.

Метки, правила и таблица «тип и стадия → скилл» описаны в корневом `AGENTS.md`, раздел «Задачи: GitHub Issues». Перед работой прочитай этот раздел. Скилл следует этой таблице, своей копии у него нет.

## Шаги

1. **Прочитай issue:**

   ```bash
   gh issue view N --json number,title,body,labels,state,parent,subIssues,blockedBy,comments
   ```

   Исходная постановка — в тексте issue. Результат прошлых шагов — в последних комментариях. Если человек не назвал номер, а попросил «любой баг», покажи список через `gh issue list --label type:bug --label stage:ready` и спроси, какой брать.

2. **Проверь, можно ли начинать.**
   - Issue закрыт: скажи об этом и остановись.
   - Нет меток типа или стадии: предложи их по `AGENTS.md` и поставь после «да».
   - Есть открытые issues в `blockedBy`: назови их и предложи начать с них.
   - Есть подзадачи: покажи их со стадиями. Если какая-то подзадача не в `stage:ready`, предложи начать с нее. Родитель переходит в `stage:ready`, только когда готовы все подзадачи.

3. **Назови следующий шаг.** Скилл по таблице, почему именно он и что он получит на вход. Жди «да».

4. **Подготовь ветку**, если шаг меняет код или создает `SPEC.md`. Работай не в main. Имя ветки: `<тип>/<N>-<кратко>`, например `fix/12-token-in-log`.

5. **Запусти скилл.** На вход дай текст issue и последний комментарий с результатом. Особенности по стадиям ниже.

6. **Запиши результат.** Покажи черновик комментария и новую стадию. После «да»:

   ```bash
   gh issue comment N --body-file - <<'EOF'
   ...
   EOF
   gh issue edit N --remove-label "stage:discuss" --add-label "stage:spec"
   ```

7. **Отметь выполненные пункты** в разделе «Готово, когда». Отмечай только пункт, который проверен: тест проходит, команда из «Как проверить» дает нужный результат. Меняй только `- [ ]` на `- [x]` в строке пункта, остальной текст не трогай:

   ```bash
   gh issue view N --json body -q .body > /tmp/issue-N.md
   # В /tmp/issue-N.md замени "- [ ]" на "- [x]" в строках выполненных пунктов.
   gh issue edit N --body-file /tmp/issue-N.md
   ```

   Перед `gh issue edit` покажи `diff` старого и нового текста: в нем должны поменяться только галочки. Если пункт не выполнен, оставь его пустым и напиши человеку почему.

8. **Перед мержем** напомни о проверке через `/agent-skills:review`. Затем PR со строкой `Closes #N` в описании. Если в ветке есть `SPEC.md` или `tasks/`, удали их последним коммитом.

## Стадии

### `stage:discuss`

- `type:feature`, `type:refactor`: запусти `interview-me`. Вход — текст issue и открытые вопросы из него.
- `type:bug`: запусти `debugging-and-error-recovery`. Цель шага — найти причину, исправлять пока не нужно.

Комментарий: для `interview-me` — подтвержденное описание намерения целиком. Для бага — причина, как воспроизвести, где в коде. Новая стадия — по трем вопросам из `AGENTS.md`.

### `stage:idea`

Запусти `idea-refine`. Комментарий: выбранный вариант, почему он, какие варианты отброшены и почему. Новая стадия — `stage:spec` или `stage:ready`.

Если человек решил задачу не делать, стадию не меняй. Предложи ему закрыть issue как not planned и напиши причину в комментарии.

### `stage:spec`

1. `/spec`: вход — текст issue и комментарии с результатами. `SPEC.md` остается в рабочей ветке.
2. `/plan`: каждую задачу плана заведи дочерним issue через `gh issue create --parent N`, с метками и текстом по шаблону скилла `issue-add`. Зависимости поставь через `--add-blocked-by`.
3. Комментарий в родителе: список подзадач по порядку и ключевые решения из спеки. Спека удалится вместе с веткой, поэтому важное перенеси в комментарий или в ADR.
4. Родитель переходит в `stage:ready`, только если все подзадачи в `stage:ready`. Иначе он остается в `stage:spec`.

### `stage:ready`

- Есть подзадачи: `/build`. Он идет по плану и закрывает подзадачи коммитами с `Closes #M`.
- Нет подзадач: `/test` для `type:bug` и `type:feature`, `/code-simplify` для `type:refactor`.

Если задача оказалась больше одного захода, остановись. Предложи сменить стадию на `stage:spec` и напиши в комментарии почему.

Комментарий после шага не нужен: результат виден в PR. Стадию не меняй, issue закроет мерж PR.

## Правила

- Не переписывай исходный текст issue. Менять можно только галочки в «Готово, когда», см. шаг 7. Исключение — задачу переформулировали целиком, порядок описан в правилах `AGENTS.md`.
- Не закрывай issues вручную. Задачу, которую решили не делать, закрывает человек.
- Не запускай следующий скилл без «да» человека.
- Замечания, которые человек откладывает по ходу работы, заводи через `issue-add`.
