# issue-add

Скилл превращает замечание из разговора в issue, которое можно взять в работу без этого разговора. Агент через неделю увидит только текст issue. Все, что нужно для работы, должно быть в нем.

Метки, вопросы для выбора стадии и таблица «тип и стадия → скилл» описаны в корневом `AGENTS.md`, раздел «Задачи: GitHub Issues». Перед работой прочитай этот раздел.

## Шаги

1. **Определи, какие пункты заводить.** Человек обычно называет пункты из списка ревью. Если непонятно, какие именно, спроси. Один issue — одна проблема. Если в пункте две проблемы, заведи два issue.

2. **Собери факты по каждому пункту.** Открой код и проверь, что проблема на месте. Запиши путь, имя функции и номер строки. Номер строки сдвигается при правках, поэтому главная привязка — имя функции. Если строка кода важна для понимания, процитируй ее в issue.

3. **Выбери тип и стадию** по `AGENTS.md`. Для стадии ответь на три вопроса оттуда и запиши ответы: они пойдут в раздел «Стадия» issue.

4. **Покажи черновики всех issues одним сообщением.** Для каждого: заголовок, метки, текст. Жди явного «да». Если человек правит, исправь и покажи снова.

5. **Проверь метки** командой `gh label list`. Если каких-то меток нет, создай их (цвета ниже).

6. **Создай issues.** Текст передавай через `--body-file -`, чтобы не было проблем с кавычками:

   ```bash
   gh issue create --title "..." --label "type:bug,stage:ready" --body-file - <<'EOF'
   ...
   EOF
   ```

   Подзадачу заводи с `--parent N`. Зависимость ставь через `gh issue edit N --add-blocked-by M`.

7. **Перечисли созданные issues** с номерами и ссылками.

## Шаблон issue

Заголовок: что не так или что нужно, обычными словами, до 72 символов. Без префиксов вроде `fix:`.

```markdown
## Что не так

Факт: что происходит сейчас и чем это отличается от нужного.
Для `type:feature`: что нужно и кому.
Для `stage:discuss`: что наблюдаем. Решение не предлагай.

## Где

- `desktop/windows/src/main/meeting/detector.ts`, функция `detectMeeting`, около строки 42 (коммит `abc1234`)

## Почему это важно

Что случится, если не исправить. Для кого.

## Готово, когда

- [ ] Проверяемый критерий
- [ ] Еще один

## Как проверить

Команда или шаги: `npx pnpm@10 exec vitest run src/main/meeting` в `desktop/windows`, `python -m pytest tests/unit/test_x.py` в `backend`, что сделать в приложении и что должно произойти.

## Стадия

`type:bug`, `stage:ready`. Причина известна: ... Хватит одного захода: правка в одной функции.
Начинать с `/test` (agent-skills): тест воспроизводит баг, потом исправление.

## Откуда

Ревью PR #N / ревью коммитов `abc1234..def5678` / замечание при работе над #M.
```

Для `stage:discuss` и `stage:idea` раздел «Готово, когда» описывает результат обсуждения, а не кода. Добавь раздел «Открытые вопросы» со списком того, что надо выяснить.

## Правила

- Не ссылайся на `SPEC.md`, `tasks/` и на разговор. Эти файлы удаляются, а разговор следующий агент не увидит.
- Коммит в разделе «Где» бери из `git rev-parse --short HEAD`. Если код с проблемой еще не закоммичен, так и напиши.
- Пиши по-русски. Имена из кода, команды и пути — в бэктиках.
- Ничего не исправляй в коде. Скилл только заводит issues.

## Цвета меток

| Метка | Цвет | Описание |
|---|---|---|
| `type:bug` | `d73a4a` | Поведение расходится с ожидаемым |
| `type:feature` | `a2eeef` | Новое поведение |
| `type:refactor` | `c5def5` | Код меняется, поведение нет |
| `stage:discuss` | `fbca04` | Неясна цель или причина бага |
| `stage:idea` | `f9d0c4` | Цель ясна, решение не выбрано |
| `stage:spec` | `bfd4f2` | Нужны спека и план |
| `stage:ready` | `0e8a16` | Можно делать |

```bash
gh label create "type:bug" --color d73a4a --description "Поведение расходится с ожидаемым"
```
