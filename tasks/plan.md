# План: определение созвона на Linux

Спецификация: `SPEC-meeting-detection-linux.md`. Задачи по шагам: `tasks/todo.md`.
Все пути ниже относительно `desktop/windows`, если не сказано иное.

## Обзор

Автомат `detector.ts`, сопоставление `patterns.ts` и оркестратор `meetingMonitor.ts` уже работают для любой ОС. На Linux не хватает трех источников сигналов (процессы, микрофон, смена окна) и запуска монитора. План: сначала собрать реальные данные с машины (выводы `pw-dump`, имена процессов, заголовки вкладок), потом довести до рабочего состояния один сценарий целиком (звонок в Telegram), затем браузер, затем российские программы, в конце замеры и changelog.

## Что выяснилось при чтении кода

1. **`pw-dump` нельзя вызывать синхронно.** `computeSignals()` синхронный и работает в main-процессе Electron. Синхронный `pw-dump` на 0,23 с каждые 2 с будет подвешивать интерфейс. Решение: наблюдатель запускает `pw-dump` асинхронно (`execFile`), хранит последний набор id в памяти, а `readMicCaptureEntries()` на Linux отдает этот кэш. Интерфейс модуля для `meetingMonitor.ts` не меняется.
2. **`subscribeForegroundChange` общий.** Его вызывают `usage/foregroundMonitor.ts` (на Linux тоже), `rewind/foregroundCaptureTrigger.ts` и `automation/foregroundTarget.ts` (эти два только на `win32`). Опрос на Linux затронет учет времени в программах: он начнет получать события смены окна. Это безвредно и даже точнее, но это изменение поведения вне модуля созвонов. Чтобы не плодить по таймеру на подписчика, делаем один общий таймер на все подписки.
3. **`nativeForeground.degrade.test.ts` требует**, чтобы без X11 `subscribeForegroundChange` возвращал пустую отписку. Опрос включаем только при `linuxAvailable()`.
4. **Чтение окна стоит 4 запуска `xprop`** (id окна, pid, id окна, заголовок), все синхронные. Раз в 2 с это несколько миллисекунд блокировки main-процесса. Проверяем по критерию 4; если дорого — читать id окна один раз и переходить на `xprop -spy`.
5. **Задержка до окна «Записать?» может превысить 5 с.** Худший случай: опрос 2 с + `pw-dump` 0,23 с + склейка 250 мс + `DEBOUNCE_MS` 3 с ≈ 5,5 с. Критерий 2 под угрозой. См. «Открытые вопросы».
6. **Имена процессов на Linux без `.exe`**, и `exeBasename` уже понимает `/`. Сопоставление для браузера сходится само: `/opt/google/chrome/chrome` дает `chrome` и в Tier 1 (активное окно), и в Tier 2 (`application.process.binary`).
7. **Ловушки `/proc`:** после обновления пакета `readlink` дает `.../telegram (deleted)`, суффикс надо срезать; `comm` обрезан до 15 символов (`telegram-deskto`), поэтому запасной путь через `comm` для длинных имен не совпадет с шаблоном. Учитываем в тестах.
8. **Самоисключение Omi:** в `pnpm dev` это `electron`, в собранном приложении — имя бинарника Omi. Берем из `process.execPath`, как на Windows.
9. PR в upstream не делаем, только забираем изменения из `BasedHardware/omi`. Поэтому правки в общих файлах (`processSnapshot.ts`, `micConsentStore.ts`, `meetingMonitor.ts`, `nativeForeground.ts`, `patterns.json`) держим минимальными: одна ветка `linux` в начале функции, логика — в новых файлах. Так слияния с upstream будут проходить без конфликтов.

## Архитектурные решения

- Разбор данных — чистые функции (`parsePwDumpMicEntries`, разбор `/proc` с внедряемым `read`), ввод-вывод — тонкие обертки, которые не бросают исключений. Так же устроен `linuxForeground.ts`.
- Новый код — в новых файлах, в общих файлах только короткие вызовы. Это снижает конфликты при слиянии с upstream.
- Ветки `win32` в `processSnapshot.ts`, `micConsentStore.ts`, `nativeForeground.ts` не трогаем, добавляем отдельную ветку `linux` перед ними.
- Опрос раз в 2 с на старте. События (`pw-dump --monitor`, `xprop -spy`) — только если замеры покажут, что опрос дорогой или медленный.
- `detector.ts` не меняем. Если для eXpress понадобится логика решений, это отдельное согласование.
- Linux-имена дописываем в существующие записи `patterns.json` (`zoom` → `["zoom.exe", "cpthost.exe", "zoom"]`), отдельный формат для ОС не вводим.

## Граф зависимостей

```
T1 окружение и базовые тесты
 └─ T2 сбор данных с машины (фикстуры, имена, заголовки, eXpress)
     │
     ├─ T3 Tier 2: разбор pw-dump (чистая функция + тесты на фикстурах)
     ├─ T4 Tier 1: процессы из /proc (+ тесты)
     │    │
     │    └─ T5 (зависит от T3, T4) подключение: наблюдатель, ветки linux,
     │          запуск монитора, шаблон telegram → звонок в Telegram работает
     │           │
     │           ├─ T6 смена окна + браузеры Linux → Meet в Chrome работает
     │           └─ T7 российские программы и заголовки (+ решение по eXpress)
     │                │
     │                └─ T8 замеры: CPU, задержка, час без ложных окон
     │                     └─ T9 changelog, проверка Windows, слияние с upstream
     │
T10 заметки «пожить пару дней» — параллельно, не блокирует
```

T3 и T4 независимы, их можно делать параллельно.

## Риски

| Риск | Влияние | Что делаем |
|---|---|---|
| eXpress держит микрофон постоянно → ложные окна | Высокое | T2 проверяет первым делом; варианты на контрольной точке 1 |
| Задержка > 5 с из-за опроса 2 с + debounce 3 с | Среднее | Замер в T8; варианты в открытых вопросах |
| Синхронный `pw-dump` подвешивает интерфейс | Высокое | Асинхронный опрос с кэшем, заложено в T5 |
| Опрос `xprop` и `pw-dump` дороже 2% ядра | Среднее | Замер в T8; запасной путь — события |
| Опрос окна меняет поведение учета времени на Linux | Низкое | Прогон тестов `src/main/usage` |
| Конфликты при слиянии с upstream в общих файлах | Среднее | Логика в новых файлах, в общих — одна ветка `linux` |
| Flatpak/Snap: другое `application.process.binary` | Среднее | T2 фиксирует факты; поддержка — по решению на контрольной точке 1 |
| Существующие тесты падают на Linux и маскируют регрессии | Среднее | База в T1, сравнение по списку, а не по числу |

## Открытые вопросы

1. **Критерий 2 (5 с).** Опрос 2 с плюс debounce 3 с дают до 5,5 с. Варианты: опрос раз в 1 с (дороже по CPU), сразу `pw-dump --monitor`, или смягчить критерий до 6 с. Менять `DEBOUNCE_MS` — это логика решений, нужно ваше согласие. Начинаем с 2 с, решаем по замерам в T8.
2. **Сценарий 6: останавливать ли опрос `pw-dump` в режиме `off`.** Пока не решено. Сейчас при `off` монитор только пропускает проверку, а опрос продолжится. Вернуться к вопросу перед T5.
3. **eXpress.** Проверяем в T2, решаем на контрольной точке 1.
