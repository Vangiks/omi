# План: локальный бэкенд

Спецификация: `SPEC-local-backend.md`. Задачи по шагам: `tasks/local-backend/todo.md`.
Пути ниже относительно корня репо.

## Обзор

Сначала поднимаем бэкенд в Docker и проверяем его без клиента: эмуляторы, сервисы, вход, разговор из WAV-файла. Потом переключаем клиент: доступ к локальным адресам, вход, чат, запись. В конце закрываем утечки (аналитика, ссылки, исходящие запросы) и проверяем, что за полдня работы в контур Omi не ушло ничего.

## Что выяснилось при чтении кода

1. **Стенд `make dev-up` — готовый образец окружения.** Переменные окружения для всех сервисов собраны в `scripts/dev-harness/dev_harness/config.py:357-448`, порты в `:14-20`. Compose повторяет их с адресами контейнеров вместо `127.0.0.1`.
2. **Эмуляторы слушают `127.0.0.1`** в корневом `firebase.json`. В контейнере нужен `0.0.0.0`. Версия `firebase-tools` закреплена в корневом `package.json`, стенд запускает с `--import` и `--export-on-exit` (`cli.py:665-708`).
3. **Файловое хранилище вместо GCS** включается при четырех условиях (`backend/utils/other/local_storage.py:30-45`). Без них бэкенд упадет при первой загрузке файла.
4. **`pusher` стенд не запускает**, а без него разговоры не завершаются. Ему нужен `MEMORY_ENABLED=on` (`backend/pusher/main.py:37`), бэкенду — `HOSTED_PUSHER_API_URL`. Готовый пример окружения для пары бэкенд и `pusher`: `backend/testing/listen_pusher_stack/run.py:205-240`.
5. **Образы ссылаются на закрытый реестр Omi** (`gcr.io/based-hardware-dev/python:3.11-slim-forky`). Подменяем аргументом сборки. У шлюза своего Dockerfile нет: используем образ бэкенда с другой командой.
6. **Клиент упрется в три барьера раньше, чем в бэкенд:** CSP во всех четырех HTML-входах, список CORS в `src/main/index.ts:711` и зашитый адрес записи в `omiListen.ts`. А чат на `pi_mono` упрется в проверку подписи токена, которую токены эмулятора не проходят.
7. **PostHog шлет события всегда:** при пустом ключе подставляется зашитый (`analytics.ts:11`). Sentry без DSN выключен, проверка обновлений на Linux не работает.

## Решения

- **Compose в `deploy/local/`, вне `backend/`.** Это настройка форка, а не код бэкенда, и так он не мешает слияниям с upstream.
- **Порты как у стенда:** 8000 (бэкенд), 10201 (`desktop-backend`), 8085 и 9099 (эмуляторы). Чтобы документация и привычки стенда подходили и здесь.
- **Секреты генерирует `init.sh`** в `deploy/local/.env`, а не копируются из стенда: у стенда `ENCRYPTION_SECRET` и `ADMIN_KEY` — заглушки из репо.
- **Изменения клиента включаются по переменным профиля**, без отдельной ветки кода. Без профиля поведение прежнее, это проверяют существующие тесты.
- **Платные проверки — отдельным флагом** `smoke.sh --paid` и только с моего разрешения.

## Граф зависимостей

```
T1 эмуляторы в контейнере и сохранение данных
 └── T2 бэкенд, шлюз, desktop-backend, Redis, Typesense; init.sh; smoke без денег
      └── T3 pusher и Deepgram; smoke --paid (нужен LLM: llm-openrouter T2–T3 или прямой ключ)
           │
T4 клиент: профиль, CSP, CORS ──────────┐
 └── T5 вход через эмулятор             │ (T4–T7 после T2)
      ├── T6 проверка токена → чат       │
      └── T7 адрес записи → запись ──────┘ (T7 после T3)
T8 аналитика, ссылки, pi-mono (после T4)
T9 ограничение исходящих запросов (после T4)
T10 проверка исходящих запросов бэкенда, замеры, README (после всех)
```

Клиентские задачи T4–T6 можно делать параллельно с T3. T8 и T9 независимы друг от друга.

## Риски

| Риск | Влияние | Что делаем |
|---|---|---|
| Эмулятор теряет данные при остановке контейнера | Высокое: пропадают разговоры | T1 первым делом проверяет сохранение; при сбое — периодический экспорт по таймеру |
| Бэкенд при старте требует облачные переменные, которых нет в стенде | Среднее | Переменные берем из стенда; T2 запускает каждый сервис по одному и читает ошибки старта |
| Распознавание через Deepgram не выбирается настройками `STT_SERVICE_MODELS` | Высокое: нет расшифровок | T3 начинается с чтения `utils/stt/streaming.py` и `config/stt_provider_policy.py` |
| Эмулятор съедает память на больших объемах | Низкое сейчас | Замер в T10, решение в `ru-backend` |
| Правка проверки токена ослабит безопасность обычной сборки | Высокое | Режим эмулятора задается при сборке; тест безопасности: обычная сборка отвергает неподписанный токен |
