# Локальный бэкенд Omi

Бэкенд Omi в Docker для одного пользователя. Спецификация: `SPEC-local-backend.md`, задачи: `tasks/local-backend/`.

Команды ниже выполняются из `deploy/local`.

## Запуск

```bash
./init.sh                    # создает .env: случайные секреты и ключи провайдеров
docker compose up -d --build --wait
./smoke.sh                   # бесплатная проверка: сервисы, вход, запрос с токеном
```

Первая сборка идет несколько минут, следующие запуски — меньше минуты.

`init.sh` спрашивает ключи OpenAI, Anthropic, Gemini, Perplexity и Deepgram. Любой можно пропустить и потом вписать в `.env`. После правки `.env` пересоздайте контейнеры командой `docker compose up -d`.

`.env` не попадает в git. В нем лежит `ENCRYPTION_SECRET`, которым зашифрованы данные пользователя в Firestore. Без него данные не прочитать, поэтому копируйте `.env` вместе с volume. Если `.env` уже есть, `init.sh` его не перезапишет.

## Сервисы

| Сервис | Что делает | Порт на `127.0.0.1` |
|---|---|---|
| `firebase` | эмуляторы Firestore и Auth, проект `demo-omi-local` | 8085, 9099 |
| `redis` | кэш, на диск не пишет | — |
| `typesense` | поиск по словам | — |
| `llm-gateway` | шлюз к провайдерам моделей | — |
| `backend` | основной API, клиент ходит сюда | 8000 |
| `desktop-backend` | API для части функций десктопа | 10201 |

`storage-init` запускается один раз перед остальными и отдает volume `storage` пользователю, от имени которого работает бэкенд. В `docker compose ps -a` он виден как `Exited (0)`, так и должно быть.

Версия `firebase-tools` в `compose.yaml` должна совпадать с версией в корневом `package.json`.

Журналы сервиса: `docker compose logs -f backend`.

## Где хранятся данные

| Volume | Что в нем |
|---|---|
| `omi-local_emulator-data` | Firestore и пользователи Auth |
| `omi-local_storage` | файлы, которые в облаке Omi лежат в GCS: записи, вложения чата |
| `omi-local_typesense-data` | поисковый индекс |

Пока эмулятор работает, данные Firestore и Auth лежат у него в памяти. На диск они попадают двумя путями:

- при остановке контейнера эмулятор выгружает их сам (`--export-on-exit`);
- раз в 5 минут контейнер сохраняет снимок. Интервал задает `FIREBASE_SNAPSHOT_INTERVAL` в `.env` в секундах, `0` выключает снимки.

При старте эмулятор загружает последнюю выгрузку.

| Что произошло | Данные |
|---|---|
| `docker compose down` | сохраняются |
| `docker compose stop` | сохраняются |
| Перезагрузка или выключение компьютера | сохраняются: Docker останавливает контейнер так же, как `stop`. После загрузки compose нужно поднять вручную |
| `docker compose kill`, сбой питания, нехватка памяти | теряются изменения после последнего снимка, то есть не больше чем за 5 минут |
| `docker compose down -v` | удаляются все |

На выгрузку при остановке отведено 60 секунд (`stop_grace_period`). Если данных станет так много, что выгрузка не успевает, Docker убьет контейнер и изменения после последнего снимка пропадут. Тогда нужно увеличить `stop_grace_period`.

Сбросить базу:

```bash
docker compose down -v
```
